# BUG-004: Changing email or username to one already in use returns 500

| | |
|---|---|
| **Status** | Open |
| **Severity** | Medium (the user sees an error and nothing is corrupted, but 500 hides a normal validation case and hurts error handling) |
| **Priority** | P3 |
| **Found by** | Exploratory API probe while writing the settings tests |
| **Found on** | 2026-11-10 |
| **Component** | API `PUT /api/user` |
| **Environment** | Local Docker stack, API `:3100` |

## Steps to reproduce
1. Register users A and B.
2. As B: `PUT /api/user` with `{"user":{"email":"<A's email>"}}` (or `{"user":{"username":"<A's username>"}}`).

## Expected
A client error, consistent with registration: **409 Conflict** (or 422) with a clear message.

## Actual

| Request | Status |
|---|---|
| `POST /api/users` with A's email | **409** (correct) |
| `POST /api/users` with A's username | **409** (correct) |
| `PUT /api/user` with A's email | **500** |
| `PUT /api/user` with A's username | **500** |

## Suspected cause
The update path does not handle the database unique-constraint error that the register path maps to 409, so it surfaces as an unhandled server error.

## Automation
`tests/settings.spec.ts` › "changing the email to one that is already taken is rejected" checks only what the user sees (an error, no redirect). The 500 status itself is API-level and will be asserted in `api-tests/`.
